# プロジェクトのフォルダ

`games/<プロジェクト名>/` に作る。部門の番号とフォルダの番号を揃える。

```
games/<プロジェクト名>/
├── 進行表.md            いまの部門、ゲートの記録、決めたこと（プロデューサーが書く）
├── 開発チーム.md        このプロジェクトだけの違い（なければ既定で動く）
├── README.md            遊び方、起動方法、ビルド・テストのコマンド
├── 01_企画/             企画書.md、市場調査.md、アイデア出し.md
├── 02_プリプロ/         デザインの柱.md、技術選定.md、アートディレクション.md、計画.md
├── 03_仕様/             GDD.md、機能仕様/<機能>.md、パラメータ表.md(.csv)、tools/
├── 04_プロト/           <問いの名前>/（捨てる前提のコード）、プレイテスト記録.md
├── 05_開発基盤/         アーキテクチャ.md、コーディング規約.md、バックログ.md、パイプライン.md
├── 06_システム/         AI.md、画面遷移.md など、実装に付く設計メモ
├── 07_コンテンツ/       レベル/、シナリオ/、アセット一覧.md、サウンド一覧.md
├── 08_統合/             統合記録.md、演出指示.md
├── 09_アルファ/         判定.md、プレイテスト記録.md
├── 10_ベータ/           バグ表.md、調整記録.md、初見テスト記録.md
├── 11_QA/               テスト計画.md、テスト結果.md、審査.md、リリース判定.md
├── 12_保守/             不具合受付.md、パッチノート.md、アップデート計画.md、分析/
├── 文書の目次.md        文書の一覧と持ち主（game-pm-secretary）
├── src/                 本番のコード
├── assets/              絵、音、テキスト（text/ja.json など）、レベルのデータ
└── tests/               自動テスト
```

- 見る担当の返事（レビュー、判定、プレイテスト）は、プロデューサーがその部門のフォルダに記録として書く
- 小さなゲームでは、使わないフォルダは作らなくてよい

## 進行表.md

プロデューサーが書く。仕事人は読むだけ。

```markdown
# 進行表：<プロジェクト名>

## いま
- 部門：06 ゲームシステム
- マイルストーン：アルファに向けて
- 次にやること：<タスクID と担当>

## 一文の企画
<企画書の一文をそのまま>

## デザインの柱
1. ...
2. ...

## ゲートの記録
| 日付 | ゲート | 結果 | 決めた人 | メモ |
|---|---|---|---|---|
| 2026-11-18 | A 企画 | 通る | オーナー | 規模はMVPで |

## 決めたこと（あとから変えるときは、ここに理由を書く）
- 2026-11-18：対象はブラウザ（PC）。スマホはリリース後

## 未決
- <決めること>（決める人、期限）
```

## 開発チーム.md

そのプロジェクトだけの違いを書く。書いていないことは既定で動く。

| 項目 | 書くこと | 既定 |
|---|---|---|
| 規模 | 小さなゲーム（近道を使う）／ふつう | ふつう |
| 使う仕事人 | 加わる仕事人（`reference/roster.md`）のうち、このプロジェクトで呼ぶ人 | 中心の35人＋監修（ディレクター職）＋そのゲームに要る専門家 |
| 使わない仕事人 | 例：音なしのゲームなので `game-content-sound` は呼ばない | なし |
| 足す観点 | 仕事人ごとに、見てほしいこと（例：`game-sys-code-review` に「モバイルの性能」） | なし |
| オーナーに見せるもの | ゲートごとに、何を見せるか（ビルド、スクショ、文書） | ゲートA〜Dで要約と遊べるビルド |
| 技術の決め | エンジン、言語、対象端末 | 技術選定で決める |
| 表記 | 用語、表記ゆれのルール | シナリオの設定.md |
