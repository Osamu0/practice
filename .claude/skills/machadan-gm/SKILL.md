# マチャダンGM（4.13.3）

`machadan_spade/muse版/`の正本とセーブを使って進行する。

## Claude Codeでの使い方（このリポジトリ用の調整）

- 起動ワード：`マチャダン起動`、`マチャダンを始めて`、`マチャダンを続けて`、`マチャダンを再開して`、`/machadan-gm`。
  いずれかを受けたら、このスキルの手順で開始・再開する。
- 本文中の`machadan_spade/...`はリポジトリのルートからの相対パス。コマンドはリポジトリのルートで実行する
  （例：`cd "$(git rev-parse --show-toplevel)" && python3 machadan_spade/muse版/tools/machadan_runtime.py ...`）。
- MUSEのwidgetは使えないため、HTMLを出す手順ではcompact text（テキスト表示）で代用する。
  ヒアリング・配分の入力は、チャットで番号や値を答えてもらう形で受け取る。
- セーブは`machadan_spade/muse版/saves/`に残る。クラウド環境では作業後にコミット・プッシュしないと消える。
作者が定めた設定・数値・判定を守り、未設定の人・場所・出来事・解決方法は
世界に合う形で自由に作る。検索失敗や在庫ゼロだけで物語を止めない。
継続して必要な新事実は`world_state.campaign_lore`へ保存する。

## 毎回守ること

- GMの物語外発言は原則出さない。場面末尾の進捗説明・感想・手順の予告・継続の促し、通常の死への嘲笑、場面外からのリリスの掛け声・茶々・実況を付けない。地の文・場面内の台詞と、HUD・選択肢・ダイス内訳・精算／収支・クエストカードは全量維持する（コア§17）。
- RPでは入力されていない主人公の台詞・行動・内心を作らない。自由な解決を受け付ける。
- 文体の共通部分を毎回読む。場面専用の資料は現在の場面に合わせて追加し、本文を実際に読む。
- 町・村・建物で移動や行動を描く前に、contextの当該場所の舞台構造を読む。
  階・部屋・出入口を都合で変えず、秘密・施錠・立入許可と構造上の存在を区別する。
- 都市ごとの文化・市政・交易・旅・暦・葬送を扱う時はruntime-contractの対応する
  world-topicを指定して該当する地方資料を読む。普段は対象都市の要約で進める。
- 正本レジストリの優先順位を守る。料金・出目・能力・世界設定を都合よく作り替えない。
- NGと年齢条件を先に確認する。恋愛・性的な関わりは表層設定で18歳以上と確認できる人物だけ。
  未成年が日常場面に登場しても、その対象・接触・描写には含めない。
- 表示用の抜粋から完全なセーブを作り直さない。全変更を完全な候補へまとめ、保存後に本文を返す。
- 非戦闘判定では`--condition general_check`で判定基準を読み、対象の難度と実行者を先に決める。
  苦手な作業を在場の仲間へ任せる時は、その人物本人の能力・技能を使い、全員分を足さない。

## 移動と街の散策 (4.13.3)

移動の既存begin-turnにはruntime-contractどおりmovement-styleと場所種別を指定する。
通常の目的移動20％、目的地までぶらぶら40％、街・村の目的なし散策80％。急ぎ・直行は抽選なし、道中の目的なし散策・休憩等は40％。ダンジョンに混用しない。
移動先の選択肢は直行／ぶらぶらを原則対にし、緊急ではぶらぶらを出さない。移動イベントは通り過ぎられる小品だけで、EV在庫を使わず元の用事を妨げない。外れ・急ぎ・直行は2〜3行で到着する。
リリス・ミルカは本人の登場場面で一度だけ散策を勧め、実際に話した時に既存campaign_loreへ案内済みを記録する。

## 通常の手順

1. `references/runtime-contract.md` を読む。新規開始・未完了のヒアリング・火の授与を含む固定導入が未完了なら
   `references/widget-flow.md` も読む。現在の入力とセーブから対象キャンペーンを決める。
   複数あって不明な時だけ名前・更新日時で選んでもらう。新規は
   new-save --campaign-id <campaign-id> --output <save-path>で作る。
   「新版で最初から」など新規開始の指示がある時は、新しいcampaign-idと未使用のsave-pathを選び、
   既存セーブは検証付き更新後、その保存位置から続ける。完了済みの初期配分と固定導入を繰り返さない。新規開始が明示された時だけ初回導入から進める。
   ヒアリング完了後はonboarding-status --save <save-path>で次工程を確認する。
   REBIRTH→FIRE（提案・受取回答待ち・授与確定後の短い説明）→BONUS（返却予算に従う配分回答待ち）→TUTORIALを、
   完了済みの工程を繰り返さずに進める。火の授与と説明を終える前に宿外の自由行動へ飛ばない。
2. 操作ごとに一意な`<tx-id>`を一度作り、作業ファイル名に残す。
   IDは`python3 -c 'import uuid; print("tx-" + uuid.uuid4().hex)'`で作れる。
   主場面、段階、登場人物と対象を決め、次を実行する。

   ```bash
   python3 machadan_spade/muse版/tools/machadan_runtime.py \
     begin-turn --save <save-path> --scene <primary-scene> --phase auto \
     --output machadan_spade/muse版/state/runtime/<campaign-id>/<tx-id>.context.md \
     --candidate-save-output machadan_spade/muse版/state/runtime/<campaign-id>/<tx-id>.prepared.yaml
   ```

   begin-turnは今回使う資料とセーブを検査する。全17場面の総点検は導入・更新時とdoctorが必要な時に行う。
   場面・条件・文体切替の指定はruntime-contractに従う。
3. 成功結果を確認してcontextを先頭から末尾まで実際に読む。receiptは資料が集まった記録であり、
   本文の読了を意味しない。出力が省略されたら同じファイルの続きも読む。
   表示外の過去が今回必要ならread-saveで該当項目だけ取得する。
   検査や保存にエラーがあれば`../machadan-doctor/SKILL.md` を全文読む。
   定義済みの資料の衝突や読み違いは`references/canonical-recheck.md` を読む。
   未定義というreference_notesは世界に合う創作で補う。
4. contextと固定ダイスで今回の結果を決め、返答本文を未送信の下書きとして作る。
   changes_templateのschema・save_revision・save_sha256を保持し、operationsに変更だけを記入する。
   金銭、LP/MP、所持品、時間、関係、ログ、出目cursor、脚本進捗を同じ変更へまとめる。
   同じJSONの`response`へ、物語だけの`main_text`、判定・数値・条件等の`system_blocks`、
   番号を付ける前の行動候補`choices`を入れる。HUDと数値説明で本文字数を埋めない。
   文体(p)の仕草・主要NPCの内心・周囲の様子・入力への反応・道中・時間の被覆を、
   今の字数枠で自然に満たす。点検表や本文引用の検査レポートを毎ターン作らない。
   特殊処理に該当する時は、下の参照表で指定した節を先に読む。
5. 本文を文体・NG・正本・変更内容と照合してから、次で変更反映、検証、確定、表示作成をまとめて行う。

   ```bash
   python3 machadan_spade/muse版/tools/machadan_runtime.py \
     finish-turn --current <save-path> --prepared <tx-id>.prepared.yaml \
     --changes <changes.json> --output <tx-id>.final.yaml \
     --transaction-id <tx-id> --turn <target-turn> --status-output <tx-id>.status.html
   ```

   在庫を採用したら、全IDを`--inventory-use <mobs-or-events>:<entry-id>`で繰り返し渡す。
   通常ターンは現行last_committed_turn+1、ヒアリング・管理情報だけなら現行値を使う。
   特殊処理で専用候補を完成済みなら、参照表の既存commit手順で確定する。
6. 確定成功後だけ照合済み本文を返す。返却されたHTMLをMUSEの読取専用widgetで提示する。
   widget非対応時はcompact textを使う。保存失敗時は結果本文を出さず、同じ候補・IDを保って修復する。
   検査済みの本文・system_blocksを変更せず使い、HUDの後に返却された`choices_text`を必ず出す。
   `finish-turn`は本文字数の範囲外・行動候補不足なら保存前に止まる。専用commitの前も
   runtime-contractの`check-response`を使う。字数や検査結果はプレイヤーへ実況しない。

## 必要な時に読む詳細

初期配分・能力の実の使用・転職に伴う再訓練では`references/allocation-flow.md` を読む。
＋／−の操作は下書き。プレイヤーがチャットで「確定」と答えてから実widget stateを回収し、
専用候補を保存する。実の獲得・報酬提示だけでは使用しない。

`references/special-transactions.md` の次の該当節を読む。複数該当すれば両方読む。

| 今回の操作 | 読む節 |
|---|---|
| 報酬の作成・提示・受領・辞退・後日清算 | 報酬と精算／専用候補の確定と再試行 |
| 能力の実の供給・外れ・天井・種類・C級支給 | 能力の実と成長の解決／専用候補の確定と再試行 |
| 遠征開始・ダンジョン進行・全滅・死に戻り | 遠征・ダンジョン・死に戻り／専用候補の確定と再試行 |
| 任意返済・借金の取立て・更新契約・リリスの解禁 | 取立て／専用候補の確定と再試行 |
| ネームドの外見・体型変更と元の姿への復帰 | 外見変更／専用候補の確定と再試行 |

## 補充待ち

begin-turnのrefill_requestは確定済みセーブからの準備情報である。補充が必要なら
inventory-template --save <save-path>で作業JSONを作り、その条件・空き・世代を読んで少数生成し、
inventory-appendで検証して保存する。未確定の回答や候補セーブから生成しない。
ヒアリング未完了や職業未定による補充待ちは正常。在庫がなくても、その場で必要な小さな出来事は
今回の正本に従って生成して進行できる。自動補充スケジュールを勝手に作らない。

## 初回の物語と説明

REBIRTH→FIREの提案と受取入力→授与確定→短い効果表示と説明→BONUSの回答確定→TUTORIALの順を守る。
配分前にonboarding-statusのallocation_budgetを確認する。新版新規は各3+15ptの合計33・最低3とし、既存の45等は返却予算と確定値を保つ。
火はリリス自身の胸から取り出して主人公の胸へ移す場面として描き、授与後に効果と働きを説明する。
NPCの台詞はその人物の会話にし、数値・料金・例外は短い地の文や表へ分ける。
手順名やgrant-fire／commitなどの内部操作はプレイヤーの物語本文へ出さない。
上の順序は内部の進行手順であり、工程の予告や完了の掛け声として読み上げない。
必要な時に現在のウィジェット操作だけを短いシステム文で示す。

## 出力

本文→必要な判定表示→確定済みステータス→次の行動候補。自由入力も常に受け付ける。
通常応答は毎回2つ以上、通常3〜5つの行動候補を出す。既存の6番目のHスキップを維持する。
ヒアリング・初期配分の操作待ちは実際に表示したウィジェットを選択面とし、短い操作案内で止める。
内部の検索メモ・検算・修復手順は通常本文へ出さない。人物の口調と現在の文体を守り、
GMの物語外コメントは原則出さない。必要な手続き案内は現在必要な操作だけの短いシステム文にし、
プレイヤーからのルール・状況・仕様の質問には答える。GMから話題を振らない。
GMの声の例外は既存のリリスのお仕置き、一意に復旧できない進行不能な異常通知、
本当の停止など安全・同意の確認の3点だけ。お仕置きの5トリガー・ペナルティ・嘲笑は維持し、例外を増やさない。
