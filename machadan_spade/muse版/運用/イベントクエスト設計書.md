# イベントクエスト設計書 (M47/M82/M83/M92 確定)

クエスト・仕事の物語化の正本。通常クエストは受注時に必ず
「クエストカード」を作り、さらに確率で「イベントクエスト」が
芽生える。どちらも **カードを先に作ってから回す**。
カードに書かれていない要素（新しい敵・真相・報酬）は
プレイ中に足さない。

カードは結末まで決めた脚本ではなく、**変わらない事実、登場人物の
目的、制約、発覚条件、利害、結果の判定規則**を持つ状況モデルである。
プレイヤーの解決手段・場面順・成功失敗・終わり方は固定しない。
想定外の案も、固定した事実と達成条件に沿うなら正規の解決として扱う。

カードの書式と部品は本書および `運用/クエスト部品表.md` に完結している。
外部の実例集は実行時に参照しない。部品をそのまま量産テンプレとして貼らず、
方向・動機・登場人物に合わせてカードを組む。

## 1. 生成の順序: 方向 → 動機付け → キー

カードは上から順に決める。順序が本体である。

- **Step 0 方向**: 面白さの型は6つ: ヒロイック（活躍・爽快）／
  感動（人情・泣ける）／コミカル（笑い）／エロ／ハラハラ
  （危機・緊張）／ほのぼの（癒し・交流）。主1つ＋副1つまで。
  親クエストの内容・登場キャラ・場所・プレイヤーの性癖設定
  から選び、NG に触れる型は選ばない。
- **推理は方向に入れない**: 謎解きを主軸にすると即興運用では
  成立が難しすぎる。真相の捻り自体は他方向のカードにも置いて
  よいし、動機付けの「放っておけない謎」は好奇心のフック
  として残す（謎解きの成立を約束しない）。
- **エロの定義**: 感動や重い物語を重ねない。エロ同人ラブコメ式
  の「スケベなシチュエーションで女の子とラッキースケベや
  いけないエッチ♡をする」こと自体が核。スケベなモンスター娘・
  山賊・盗賊の討伐や捕獲（M23）でもよく、通常クエストの解決
  ルートにエロを置いてもよい。「エロいことをするのに最適な
  シチュ」「それはもうHなことするしかないなぁ♡」という状況
  （＝スケベギミック）を用意することがエロ方向の仕事。
- **Step 1 動機付け**: 「なぜ最後までやりたくなるか」。型は:
  助けたい人がいる／放っておけない謎・違和感がある／報酬・
  得るものが魅力的／約束・義理・評判がかかる／相手に興味・
  好意がある／自分の力を試したい・見せたい。動機は最初の
  1場面の中でプレイヤーに伝わる形（hook）で設計する。
  最初の場面で「やりたい」が立たないカードは組み直す。
- **Step 2 キー**: 人物・状況・真相・解決・敵・報酬は、方向と
  動機を実現するためだけに決める。方向にも動機にも仕えない
  要素は入れない。

## 2. 人となり3点セット

NPC の人となりは **癖（行動の癖）／喋り方（口癖・声の型）／
こだわり（その人だけの価値観）** で作る。汎用的な性格語
（優しい・元気・真面目）だけで作られた人物は失敗扱いとし、
台詞1つでその人と分かる具体性を必須とする。固定キャストは
人格ファイルの癖・口癖が正本（新規に作らない）。
「何とかしてあげたくなるキャラ」も動機付けの型の一つ
（弱さと意地の両方を持たせる）。

## 3. 見せ場の設計

- 人物の見せ場・成長の場面はカードで設計する: (1) 見せ場
  そのもの（誰が・誰の前で・何を成すか） (2) 配役（その場面が
  一番劇的になる顔ぶれ） (3) 布石（先に見せておく、その人物の
  情けない姿・本音・大切なもの。布石があるからプレイヤーは
  見せ場を助けたくなる）。これは成立し得る機会の設計であり、
  プレイヤーが別の方法を選んだ時に場面や成長を強制しない。
- **見せ場の装置は1カードに1つ**。配役は選んだ装置から
  決める（装置を重ねると配役が矛盾する）。
- **「もうひとひねり」**: 本編の解決の後に置く第二の山場は、
  カードに事実と発動条件を先決めした場合のみ可。条件が成立しなければ
  出さない。即興の追加は禁止。規模の上限（§6）の中で収める。

### 3.1 物語ビート（全クエスト必須）

方向・動機・捻りを決めただけでは完成ではない。通常クエストも
イベントクエストも、最初の場面を出す前に次の5ビートで **何を
成立させるか** と感情変化の条件をカードへ固定する。これは場面を
順番どおり強制する台本ではない。プレイヤーが近道、撤退、交渉、
想定外の手段を選べば、順序の入れ替え、同一ターンへの圧縮、未到達
ビートの不発を許し、その選択から自然に生じる終わり方へ進める。

1. **導入**: 依頼人の困り方を場面で見せ、hookをプレイヤーへ渡す。
2. **展開**: 調査・出会い・試行のどれかで、最初の理解を深める。
3. **転換と選択**: 先決めした事実が発覚する条件と、競合する価値を
   決める。既知の選択肢は例であり、二択を強制しない。
4. **山場**: プレイヤーが介入できる圧力、失敗時の危険、利用可能な
   手掛かりを決める。取る行動や結果は決めない。
5. **余韻**: 最後に答えを返す論点と、結果別の人物反応の規則を持つ。
   成功前提の台詞や関係変化は固定しない。

感情線は `start`（最初に何を恐れ／望んでいるか）、
`change_conditions`（何が起きればどう揺れるか）、`payoff_rules`
（結果に応じて何へ答えるか）で固定する。単なる「作業をする→判定
1回→報酬」や、成功するまで同じ判定を繰り返す構成は失敗扱いとし、
カードを組み直す。

完成判定は次の一文が具体的に言えること: **「依頼人はXを望み、Zの
制約がある。プレイヤーが選んだ方法に応じて、Wはこの規則で変わる」**。
特定のY（解決法）を文中へ固定しなければ成立しないカードは、自由度が
足りないので組み直す。

## 4. クエストカード（通常クエスト・常時）

ギルド依頼などの通常クエストは、受注時に必ず作る。
掲示板の提示文はカードから生成する（依頼文だけが先にあって
中身が無い、を禁止）。ダンジョン潜行そのものは対象外
（ダンジョンは戦いの場）。

```
quest_card:
  quest_id: "Q-..."
  immutable_version: 1
  direction: {main, sub}
  motivation: {type, hook}
  client: ""                # 依頼人（人となり3点セットで）
  situation: ""             # 現地で何が起きているか
  twist: ""                 # 捻り1つだけ（見た目と実態のズレ。
                            #   エロ方向ではスケベギミックが核）
  climax: ""                # プレイヤーが介入できる山場の圧力・利害
  showpiece: {moment, casting, setup}
  story_beats:
    opening: {must_show: "", hook: ""}
    development: {discoverable: [], opportunities: []}
    reversal: {trigger: "", revealed_fact: "", value_conflict: ""}
    climax: {pressure: "", stakes: "", available_levers: []}
    aftermath: {must_resolve: [], reaction_rules: []}
  emotional_thread:
    start: ""
    change_conditions: []
    payoff_rules: []
  choice_space:
    pressure: ""
    known_options: []        # 例示であり網羅しない
    open_solution: true
    consequence_rules: []
  second_twist: {trigger: "", fact: ""}
                            # 任意。trigger不成立なら出さない
  resolution: {main, alt, open_solution: true}
                            # main/altは既知の例。別案も判定する
  enemies: []               # §7 の順で確定した全文
  reward_contract: {}       # §8。報酬内容・時期・受取経路・辞退を先決め
  reward_note: {type: "", condition: ""}
                            # 任意。契約外の小さなお礼: 金 / 物 / 関係の進展 /
                            # (相手と文脈が合えば) エロいお礼 (M48 C-3)。
                            # 実結果がconditionを満たす時だけ申し出る。辞退可
  carryover: "なし"
  progress: {stage: accepted, flags: [], checks_used: 0}
```

`quest_id` と受注時の依頼人、固定事実、制約、達成条件、報酬契約は不変部である。
進行は `progress` へ追記し、無言で不変部を書き換えない。条件変更は依頼人との
明示的な再交渉として、変更前後、理由、同意者、transaction IDを履歴へ残す。

`climax` と `showpiece` は山場になり得る圧力と演出、
`story_beats.climax` はその成立条件である。プレイヤーが別の方法で
圧力を解消した時は、予定場面を強制せず、その方法自体を山場として
扱う。

### 4.1 生産職・「○○屋」の製作依頼

`job_profile.expertise_tags`、現在の仕事、または `enterprise_state` に保存された
店・工房が、物品・料理・薬・衣服・魔道具・設備などを扱える時、その専門性を
見込んだ依頼を出せる。職業名だけで設備や商業資格があると推測しない。
永続状態、営業回数、未知素材、研究、レシピ、職業事件の正本は
`職業・店舗・商品開発システム.md` (M92) とする。依頼型は次の3つ。

1. **指定品製作**: 「○○を作ってほしい」。既存カテゴリだが、依頼人
   固有の制約があり既製品では足りない。改良・修理もここへ含める。
2. **新規発明**: 「○○を発明してほしい」。既製品では解決できず、
   調査と試作が要る。
3. **悩み解決**: 「こんなことで困っている」。品名ではなく達成条件を
   固定し、何を作るかはプレイヤーが考える。任せられた時だけGMが
   2〜3案を提示する。

生産依頼では通常の `quest_card` に次を追加する。

```
  work_kind: production_commission
  commission:
    order_id: "ORD-..."
    business_id: null              # 店舗外の単発仕事ならnull
    producer_role: ""              # player.job / 店・工房の役割
    request_type: ""               # 指定品製作 / 新規発明 / 悩み解決
    request_quote: ""              # 依頼人自身の言葉
    client_need: ""                # 本当に叶えたいこと
    why_now: ""                    # 今でなければならない理由
    anticipated_use_context: ""    # 想定される用途。場所や手段は拘束しない
    existing_solution_failure: ""  # 既製品では駄目な理由
    constraints: []                # 2〜3個。期限・環境・身体・予算など
    deadline: ""                   # なしなら「なし」
    budget: ""                     # 依頼人が払える上限
    available_leads: []            # 現場確認・聞き取り・測定・素材調査
    known_materials: []            # 原則は既存素材。他案も可
    provided_materials: []         # 依頼人が支給する物
    material_cost_owner_default: "依頼人"
                                    # 自腹はプレイヤーが明示選択した時だけ
    prototype:
      known_risks: []
      complication_trigger: ""     # このカードの twist と同じ問題
      test_conditions: []
    choice_space:
      pressure: ""
      known_options: []            # 例示。プレイヤーの別案を許す
      tradeoff_rules: []           # 性能対安全など。結果を導く規則
      open_solution: true
    completion_criteria: []        # 正解の品名でなく満たすべき条件
    final_use_pressure: ""         # 実演・実使用で問われるもの
    aftermath_rules: []            # 結果別の依頼人と周囲の反応
    ownership_default: "依頼人"    # 受注時の合意で変更可
    scope: routine                 # routine/specialist/major/civic
    risk_rank: D                   # E/D/C/B/A
    weirdness: ordinary            # ordinary/unusual/bizarre
    required_expertise: []
    required_facilities: []
    checks_max: 2
```

物語の基本線は **相談と困り事の実景 → 調査または素材入手 →
設計・試作と想定外 → トレードオフ → 実地使用・納品と余韻** とする。
これは利用可能なドラマの骨格であり、プレイヤーが工程を省く、順序を
変える、別の品や製作以外の解決を提案する自由を妨げない。
完成・実使用へ進んだ場合は、製作そのものではなく「初めて現場で役に
立つ瞬間」を見せ場の既定にする。別の解決、納品だけ、撤退を選んだ時は
その選択に応じた山場または閉じ方へ変える。
素材採取だけにせず、依頼人の事情、既製品が使えない理由、試作で
分かった問題、選択の結果を人物の反応へつなげる。

- `resolution.main` は生産職の専門性を見せる既知の案、`alt` は紹介・
  共同製作・応急策など職業に依存しない既知の案として持つ。ただし
  どちらも正解ルートではなく、プレイヤーの別案を同じ基準で判定する。
- 重要判定は調査・試作・実演のうち最大2回を目安とし、失敗しても
  プレイヤー自身が撤退を選んだ場合を除き、GMが「作れず終了」だけに
  固定しない。費用・日数・性能・見た目の妥協、別案、依頼人との再交渉
  などを選べる。同じ判定を成功まで繰り返さない。
- `prototype.complication_trigger` で発覚する事実を通常の `twist` と
  して扱い、別の黒幕や
  無関係な捻りを重ねない。
- 納品物は依頼人所有を既定とし、受注時の合意で変更できる。いずれの
  場合もプレイヤーの所持品や恒久バフへ自動追加しない。プレイヤー用の
  複製・レシピ・永続効果を得る場合だけ
  `Item_Database` と `魔道科学メモ` の価格・性能・技術上限に従う。
- 量産解禁、恒久施設、市場価格の変更、世界技術の恒常的な進歩も自動で
  発生させない。商用化する場合は、プレイヤーの明示選択を受けてM92の
  `recipes` へ完全仕様、原価、設備、製造時間、性能上限の物差しを保存する。
  商業レシピも自動収入・無料複製を発生させない。
- カード内だけの特殊素材は無売価として完成時に消費する。新規装備を
  無料の報酬にせず、報酬契約は§8とM43の価値目安で決める。現金成分は
  必須ではない。
- 店仕事は一律D級にせず、`scope/risk_rank/weirdness` を別々に固定する。
  日常E〜D、専門C、重大B、都市級Aを目安とし、材料費は報酬と分け、
  受注時に誰が負担するかを明示する。
- 期限、予算、支給素材、材料費負担、完成品の所有は受注時の合意として
  記録する。受注後もプレイヤーが依頼人と明示的に再交渉でき、合意した
  変更はそのターンのカード差分へ記録する。
- 受注時に材料・支給品を安定IDで予約し、予約中は使用・売却・別注文への
  流用を禁止する。消費・返却・喪失、成果物、報酬、評判を同一transactionで
  確定する。店・宿の倉庫と冒険用共有バッグの移動も明示差分にする。
- 受注条件は不変の `commission`、段階・フラグ・判定済み回数は
  `quest_card.progress`、永続する注文状態と `reservation_ids` はM92の `order_book`
  を正本とする。同じ `order_id` で結び、進行時は後2者を同一transactionで合わせる。

### 4.2 職業知識で解く事件

製作物を必要としない診断、鑑定、毒物分析、建築事故、帳簿不正、偽造判定、
故障原因、衛生問題、危険物封じは `work_kind: professional_case` とする。
カード形はM92 `[PROFESSIONAL_CASE]` を使う。

- 固定事実を最低3つ、真相へ届く証拠経路を最低2つ用意する。
- 基本観察は必ず得られ、専門性は意味・危険・原因候補のいずれかを深くする。
- 一回の失敗で必須手掛かりを消さず、時間、危険、費用、証拠の完全性、
  人間関係を変える。
- 専門職でない者も別証拠、協力者、隔離、応急策等で解決できる。
- プレイヤー案を否定するため、カード外の真相や犯人を後付けしない。

### 4.3 未知素材・研究・レシピ

未知素材は通常スタックへ名前だけで加えず、M92の `discoveries` へ取得源、
Tier、観察済み性質、封印された真相、危険性を固定する。1〜2F/E〜D級をTier1、
3〜4F/C級をTier2、5〜6F/B級をTier3、7〜9F/A級をTier4の目安とし、
未知であることを理由に既存Item Tierの上限を破らない。

研究は分析・試作・実地試験を `research_projects` に保存し、重要判定は合計2回まで。
完成品を商品化する時だけ、安定IDと完全仕様を持つ `recipes` と商品定義を作る。

### 生産依頼中にイベントクエストが発生した時

M47の30%判定でイベントが発生しても、生産依頼と無関係な別客・別注文を
横から挿さない。親依頼の物語を深める出来事として接続する。

- **A 道中型**: 実際に素材調達・運搬へ出る場合だけ使う。
- **B 現地型**: 試作時の事故、素材の性質、依頼人が伏せていた使用条件、
  現場設備の問題など。
- **C 余波型**: 納品実演で判明する問題、競合する利用者の要望、実際に
  使ったことで生じる小さな対立など。

親カードの固定事実と達成条件は変えず、イベント側にも開かれた解決と
結果規則を持たせる。親依頼を別の方法で解決してイベントの発動条件が
消えた時は、§5の置き場規則に反しない範囲で同じ親依頼に即した形へ寄せ、
無関係な事件には変えない。

## 5. イベントクエストの発動判定

- **単位**: クエストや仕事1件につき1回。ギルド依頼の受注1件／
  娼館の勤務1回（客1件）／GM が開始時に「仕事」と宣言した
  活動1件。店を開ける・工房で客を待つ行為は、M92の条件を満たす日だけ
  3候補を提示し、選ばれた1件をカード化して仕事1件と数える。同じ店舗では
  1日1回までで、進行中注文がある間は新規有償注文を生成しない。対象外: 買い物・会話・散策だけのターン、クエストを
  伴わない自由なダンジョン潜行そのもの（クエスト目的の潜行は
  そのクエストの一部として受注時に1回だけ）。
- **タイミング**: 受注（仕事の開始）が確定したターン。
  既にイベントが進行中の間は、新しい仕事で判定しない
  （同時に抱えるイベントは1つまで）。
- **方法**: d10 テープを1件消費し、**3以下で発生（30%）**。
  出目は GM が作らない（M28）。天井（連続不発の救済）はない。
- **記録**: 内部のターン差分へ `event_roll.die=d10`、出目、消費した
  カーソル位置を記録する。ユーザー向けの判定提示は
  `EVENT_ROLL: d10=<出目>` だけとし、発生の有無は書かない。
  カード内容はセーブ側にのみ置く。引き直しは禁止。
- 発生したら、最初の場面を出力する前にイベントカードを
  生成し、セーブの `active_event` へ記録する。
- **受注時のd10順**: 経済的対価のある親依頼なら、先にM43の目標報酬
  価値を1件引いて親カードを完成させ、その後に本節のイベント発生判定を
  1件引く。イベントが発生し、そのイベントにも経済的対価があるなら、
  イベントカード生成時にその目標価値をさらに1件引く。無報酬依頼では
  対応するM43ロールを消費しない。

### イベントカード様式

```
event_card:
  title: ""            # 仮タイトル（プレイヤーには見せない）
  parent: ""           # 親クエスト/仕事の名前
  type: ""             # A 道中型 / B 現地型 / C 余波型
  sprout_timing: ""    # 発生タイミング（型から1つ）
  direction: {main, sub}
  motivation: {type, hook}
  who: []              # 誰が（人となり3点セット＋年齢を明記）
  situation: ""        # どんなことが・どこで・どうやって
  truth: ""            # 真相（イベント内で全て回収する）
  resolution: {main, alt, open_solution: true}
  showpiece: {moment, casting, setup}
  story_beats:
    opening: {must_show: "", hook: ""}
    development: {discoverable: [], opportunities: []}
    reversal: {trigger: "", revealed_fact: "", value_conflict: ""}
    climax: {pressure: "", stakes: "", available_levers: []}
    aftermath: {must_resolve: [], reaction_rules: []}
  emotional_thread:
    start: ""
    change_conditions: []
    payoff_rules: []
  choice_space:
    pressure: ""
    known_options: []
    open_solution: true
    consequence_rules: []
  second_twist: {trigger: "", fact: ""}
                       # 任意。trigger不成立なら出さない
  enemies: []          # {name, count, stats全文, 出典/物差し}
  reward_contract: {}       # §8。親報酬とは別の契約
  scale: {turns_max: 8, places_max: 2, battles_max: 2}
  failure: {conditions: [], closure_rules: []}
                       # 失敗・拒否・時間切れの結果別の閉じ方
  reward_note: {type: "", condition: ""}
                       # 任意の契約外のお礼。condition成立時に申し出、辞退可
  carryover: "なし"
```

- 型: A 道中型（移動中が舞台）／B 現地型（仕事の現場・滞在中）／
  C 余波型（目的達成の直後〜報告の場面。悪役はこのイベント
  限りの存在として内で完結させる）。
- 発生タイミングは親クエストの報告より前に必ず置く。置き場が
  無くなった場合は報告シーンの頭に寄せる（発生を取り消さない）。

## 6. 生成制約（風呂敷を広げない）

1. 新規 NPC の人数に上限は設けない。代わりの歯止めは機能
   制約: 名前のある NPC は全員、真相・解決・動機付けのどれかに
   必要な役割を持つこと。役割のない者は名前を付けずモブで扱う。
   新規の敵性存在（悪役）は最大1勢力・イベント限りで完結。
2. **持ち越し要素は原則「なし」**: 未回収の謎・謎のアイテム・
   意味深な台詞・キーキャラクターの登場は禁止。真相は内で
   全て回収する。carryover 欄に「なし」と明記する。例外は、完結済みの
   完成品、評判、顧客関係、街の変化だけを根拠にしたM92の
   `aftermath_seed` であり、未解決事件や黒幕の予約には使わない。
3. 本筋（借金・ダンジョン攻略・リリスの火）へは触れない。
   イベント NPC は火を分けられない／パーティ候補にしない
   （関係は npc_relationship への記録まで）。
4. 規模の上限はカードの scale が正本（標準3〜6ターン、
   上限8ターン／場所2つまで／戦闘2エンカウントまで）。
   超えそうになったら解決条件へ収束させる。
5. 既存素材の優先: 人物・場所・敵は、まず既存キャスト／
   そのクエストで既に登場した人物・場所／Bestiary と
   Overworld の素材から選ぶ。新規生成は不足分だけ。
6. 5ビートは因果でつなぐ。偶然の遭遇を並べたり、何をしても結果が
   同じになる見せかけの分岐を作らない。実際に選ばれた方法は、固定
   した制約と `consequence_rules` により、方法・危険・関係・報酬・
   結末の少なくとも1つを変える。
7. カードへない敵・真相・制約を、プレイヤー案を潰すために後付け
   しない。想定外の行動の結果は固定済みの事実とルールから裁定し、
   そのターンの差分としてカード／セーブへ記録してから描写する。
   予定した場面が不要になったら捨て、そこへ誘導し直さない。

## 7. 敵パラメータの決め方

カード生成時に以下の優先順で確定し、全文をカードに記録する。
プレイ中のアドリブ生成はしない。

1. 数値正本 §4 / Bestiary に最終値がある敵 → そのまま使う。
   この §7 の手順は通常クエストの敵にも適用する (M75。
   Quest_Guild の難易度表は帯の確認用で、範囲値での新規生成は
   しない)。
2. Overworld の [敵]/[Q敵] のみにある敵 → 旧基準の値なので
   **全ステ +1・LP ×1.3** の再基準変換を掛けて記録する。
3. 新規の敵 → 親クエストのランク・階層帯にいる正本の敵を
   「物差し」に1体選び、その帯から作る。強さの目安は M34 の
   検証帯: イベントの敵は「強敵」帯（標準PTで勝率50〜85%）
   以下、ボス帯（35〜65%）は親クエスト C級以上のイベント
   だけに許す。物差しにした敵名を記録する。
   イベント敵は原則カード限りとし、図鑑へ追加しない
   （恒常化する場合は M42 の照合対象になる）。

## 8. 報酬契約・受取時期・受取経路（M83）

報酬は現金だけに限定しない。金、アイテム、素材、権利、施設利用、
割引、具体的なサービス、協力、紹介、価値のある情報などから、依頼者が
実際に提供でき、その物語に自然なものを選ぶ。**種類数に下限・上限は
設けない**。無報酬、1種類だけ、複数種類、全種類を含む構成のいずれも
禁止しないが、報酬欄を埋めるために不自然な対価を足してはならない。

- 金のない依頼者に現金を創作しない。品物を持つ人は品物、技能を持つ
  人は役務、権限を持つ組織は権利、人脈を持つ人は紹介などを提示できる。
- 何も差し出せない依頼者の無報酬依頼も成立する。受けるかはプレイヤー
  が決め、無報酬であることを受注前に隠さない。
- 複数報酬も、依頼者の立場やクエストの格に合えば自然である。現金＋
  記念品＋施設利用権などを一律に減らしたり禁止したりしない。
- 感謝、好感、関係変化そのものは契約対価として水増ししない。具体的な
  紹介・協力・サービスなら、その内容を報酬成分として記録できる。

通常カードとイベントカードは、生成時に次を保持する。

```
reward_contract:
  settlement_id: ""              # クエスト内で一意
  offered: true                   # 無報酬・善意依頼なら false
  payer: ""                       # 実際に渡す者・組織
  guarantor: "なし"              # ギルド等の保証・預かり先
  payer_capacity: ""              # 金・所有物・技能・権限・人脈の根拠
  composition_reason: ""          # この構成が物語上自然な理由
  value_reference:
    basis: "M43 / なし"
    rank_formula: ""
    roll: {die: d10, result: null}
    estimated_total_g: null        # 価格化不能なら null
  components:
    - component_id: ""             # settlement内で一意
      kind: ""                     # gold / item / right / service /
                                     # favor / referral / information
      description: ""
      detail: {}                    # 個数、対象、範囲、回数、期限等
      estimated_value_g: null
      provider: ""
      earn_condition: ""
      delivery_condition: ""
      state: offered               # offered / accepted / earned / due /
                                     # pending / delivered / declined / forfeited
  expenses:                        # 報酬とは別会計
    provided_materials: []
    reimbursed_costs: []
    unused_materials_rule: ""
  delivery_plan:
    - trigger: ""                  # 受注時 / 節目 / 現地完了 / 納品 /
                                     # 実使用確認 / 報告 / 後日
      component_ids: []
      route: ""                    # ギルド受付 / 依頼人から直接 /
                                     # 現地 / 代理人 / 預かり先
      place_or_contact: ""
      fallback_holder: "なし"
  outcome_rules:
    full: []
    partial: []
    failure: []
    player_cancel: []
    client_cancel: []
  renegotiable: true
  settlement_status: offered       # offered / active / partial / pending /
                                     # settled / declined / forfeited
  delivered_component_ids: []
```

`components[].detail` は空欄の自由記述ではなく、次の清算用キーを
受注時に固定する。`estimated_value_g` は上のcomponent直下の目安値とし、
detailの実体仕様と混ぜない。

- gold: `amount`
- item: `item_name`, `quantity`
- right、または後日使うservice/favor/referral/information:
  `delivery_target: world_state.entitlements` と
  `entitlement_id/name/issuer/scope/conditions/uses_remaining/expires`
- その場で完了するservice/favor/referral/information:
  `delivery_target: session_log` と `summary`。反映行は
  `reward_delivery: {settlement_id, component_id, kind, summary}` も持つ。

契約から保留へ移す時は `component_id/kind/detail` とpayerをそのまま
`pending_rewards` へ複写する。カードを消すcommitでは、全成分が
delivered/declined/forfeitedの台帳またはpendingのどれかに一度だけ移る。
台帳・保留のpayer、kind、detailを契約からすり替えない。

### 8.1 種別ごとの制約

- **金**: 有償依頼の価値目安は M43。金成分を含む時も、報酬全体との
  釣り合いを見て決める。材料費・旅費・預かり品返却は報酬に数えない。
- **アイテム・素材**: Item_Database の実在品または既存素材を優先する。
  新規品をプレイヤーが得る場合は同正本の完全仕様・価格・上限が必要。
- **権利・割引・施設利用**: 発行者、対象、場所、回数または期間、条件、
  重複可否を明記する。依頼者にその権限がなければ提示できない。
- **サービス・協力・紹介**: 誰が何を、何回、どこまで行うかを明記する。
  「何でも一つ頼める」のような無制限の約束にしない。
- **情報**: 具体的な内容と入手経路を固定し、正本にない世界の秘密や
  次編前提の謎を報酬として捏造しない。
- **能力の実**: カードに明記した場合のみ可（数値正本 §2）。最大1個、
  親クエスト C級以上または敵が強敵帯のイベントに限る。頻度目安は
  イベント10件に1件程度で、種類はドロップ表の d10 表で決める。

M43の価値帯は有償依頼のバランス目安であり、報酬ノルマではない。
物語の自然さを優先し、価値帯に届かない時は条件を受注前に明示する。
価値を合わせるために、依頼者が持たない金・品・権限を足さない。

### 8.2 受取時期と経路

- **ギルド依頼**: 原則は報告時に受付で精算。ギルドが保証・預かりを
  引き受けている時だけ、依頼人不在でも受け取れる。
- **直接依頼**: 依頼人への納品、結果確認、現地完了時など、合意した
  triggerで直接受領する。ギルドへ戻ることを強制しない。
- **生産依頼**: 支給素材・経費・前金を受注時、残りを納品または実使用
  確認後など、成分ごとに別時期を設定できる。
- **イベントクエスト**: 提供者がその場にいて条件を満たすなら終了時。
  いなければ保証人・代理人・預かり先、または保留報酬へ移す。
- **別解決・部分成功**: 解決ルート名ではなく達成条件と outcome_rules
  から、獲得した成分を決める。想定外の解決だけを理由に減額しない。
- 受取経路は交渉で変更できる。合意した変更をカード差分へ記録する。

獲得済みだが、受取意思はあるのに物理的にまだ渡せない成分だけを、
クエスト終了時に `world_state.pending_rewards` へ移す。現金は
`player.gold`、品物は `inventory_bundle`（inventory / item_definitions /
item_instances）、後日使う権利・サービス・紹介等は
`world_state.entitlements` へ移す。受領・辞退・失権の確定成分は、
`world_state.reward_ledger` に `settlement_id/component_id/state/transaction_id`
を追記する。この台帳は消去・上書きせず、同じIDを二度反映しない。
権利等の `entitlements` は元の `source_settlement_id/source_component_id`
を必ず持ち、台帳の delivered 成分と1対1で結ぶ。

delivered成分の台帳には `effect` を必ず付ける。`target` は
`player.gold` / `inventory_bundle` / `world_state.entitlements` / `session_log` の
実際の反映先とし、現行セーブと候補セーブの `before_sha256` /
`after_sha256` を記録する。金は正の `amount`、権利等は新規
`entitlement_id` も記録する。inventory_bundleは出力の `added_items` から
`item_name/quantity`、session_logは `append_only: true` を確認して
`appended_log_entries` から未使用の
`log_entry_index/log_entry_sha256` を記録する。実体の差分と一致しない候補はcommitで
拒否する。declined / forfeited は何も渡さないため `effect: null` にする。
ハッシュは実行時に `machadan_runtime.py reward-effect --current <save>
--candidate <candidate> --target <target>` で得る。

### 8.3 プレイヤーの受取拒否

プレイヤーは提示時・受取時のどちらでも、**全部受領、一部だけ受領、
全部辞退**を自由に選べる。辞退に機械的ペナルティを付けない。

- 辞退した成分は `declined` とし、金・所持品・権利へ反映しない。
- 辞退した成分を `pending_rewards` に残さず、後から自動付与しない。
- NPCが感情として再度申し出ることはあり得るが、受領を強制しない。
- `reward_note` の契約外の小さなお礼も、条件成立時に申し出るだけで、
  プレイヤーは拒否できる。
- 受領、部分受領、辞退、保留への移動は、実体の変更、ID・status更新、
  `reward_ledger` の追記を同じ候補セーブ内で行い、1回のcommitで
  確定する。保留成分を消す時は、同じ候補内に delivered / declined /
  forfeited のどれかを必ず残す。

## 9. 進行と終了

- **クリア**: プレイヤーの選んだ方法で解決条件を満たし、
  `story_beats.aftermath.reaction_rules` と
  `emotional_thread.payoff_rules` から実結果に合う余韻を描いた
  ターンで終了。reward_contractから獲得成分を確定し、その場で受領する
  成分、辞退した成分、受取意思はあるが渡せない保留成分を分ける。
  報酬受取を待つためだけにクエストを開いたままにせず、active_eventを
  消し、session_logへ1〜2行の要約を残す。
  締めは「これで終わり」と分かる形にする。
  生産・職業事件では同じcommitで注文を閉じ、予約材料、成果物、研究・
  レシピ、評判、街の変化を確定する。完結した事実から後日の別依頼が自然に
  生じ得る場合だけ、M92の `aftermath_seeds` へ `dormant` で保存できる。
- **戦闘敗北**: 通常の敗北処理（Phase D、火の死に戻り条件は
  通常どおり）が発動し、イベントは「失敗で終了」として閉じる。
  リトライのループは作らない。真相は未回収のまま閉じてよい
  （その悪役・事件は世界から退場したものとして扱う）。
- **拒否・無関与**: プレイヤーが断る・聞き流す等を選んだら、
  その場で終了し、ペナルティはない。「断る」も正規の解決。
- **時間切れ**: 親クエストの期限・場面の区切りが来たら親を
  優先し、イベントは未解決のまま閉じる（記録のみ）。

M92の生産依頼・職業事件に限り、戦闘敗北や期限切れも「不明のまま次回へ」とは
しない。受注時の `consequence_rules` に従って失敗結果、依頼人の反応、固定した
原因の帰結、材料と契約の行き先を描き、その回の注文と事件を閉じる。悪い結果は
あってよいが、同じ未解決案件を再開する種は残さない。

## 10. 続編と完結結果の再利用

広げてよいのは、プレイヤーの入力が実際に次のどちらかに
当てはまる時だけ。

1. イベント終了の提示の後も、プレイヤーが自発的に追跡・
   調査・聞き込みを続けている。
2. 「黒幕がいるはず」「もっと知りたい」等の明示的な
   継続意思が入力された。

- 続ける場合は、その場で続編カードを新規に生成してから
  続ける（キーの先行確定は続編でも守る。規模・持ち越し禁止も
  同じ）。GM 側からは続編の種を一切置かない。
- 判断に迷ったら広げない（既定は終了）。

上記は、完結した結果をM92の `aftermath_seeds` へ保存することを妨げない。
これは続編予約ではなく、「完成した商品を見た別人から依頼が来る」「助けた客が
別の客を紹介する」等の因果の候補である。採用時は後日、新しい独立カードを作る。
採用されなくても未解決、失敗、伏線放置とは扱わない。

## 11. 素材（Overworld 等）の変換規則

`生成/Overworld_Encounters.md` は素材庫として使う。元の
1d6 道中表は本設計の発動判定に置き換え済みで、二重に振らない。
素材をカードへ書き写す前に以下を必須とする。

1. **成人化**: 登場人物は全員18歳以上の成人として再定義する。
   素材側の古い年齢・外見表記（未成年を思わせる表現、年齢に例える
   表記）はカードへ持ち込まない。小柄・童顔などの成人の特徴
   として書き直す（コア運用ルール §2・追補）。「学園」が関わる
   素材は成人向けの学院として扱う。
2. **数値変換**: 敵は §7 の順で正本値／再基準変換値にする。
   旧式の判定式（1d6 判定等）は M33/M84 の式へ読み替える。
3. **報酬の付け替え**: 素材側の報酬（仲間候補化・恒久バフ等）
   はそのまま採用せず、§8 の範囲へ置き換える。永続ステータス
   変動が書かれた素材は、その部分を落とす。

## 12. エロ・NG・年齢

- カード生成時にヒアリングの NG 事項（desire_data）を照合し、
  NG に触れるカードは生成しない（別のキーで組み直す）。
- ero_scene の ON/OFF と文体適用は文体ルールカード (m) の
  既存規則どおり。CNC 前提（コア §1）もそのまま適用する。
- 登場人物は全員成人。新規 NPC の年齢はカードに明記する。

## 13. セーブと表示

- クエストカードはセーブの `world_state.quest_card` に、
  イベントカードは `active_event` に保持する。カードが
  Tier A（セーブ）にあるため、進行中に本書を読み直す
  必要はない。本書を読むのは受注ターンのみ（ルーティング表
  Tier B）。
- 店舗、注文、発見、研究、レシピ、商品、職業評判、街の変化、
