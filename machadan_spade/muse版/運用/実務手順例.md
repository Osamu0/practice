# 実務手順の正形 (4.13.0)

この資料は該当する管理・精算の時だけ読む。プレイヤーへキーやパスを読み上げない。
全て完全な候補ファイルに対する例で、現行セーブへ直接書き込まない。
通常のbegin-turnで得たprepared候補とreceipt・変更JSONの結び付きを維持する。

## 1. 導入とパス

新規導入のREBIRTH／FIRE／BONUSは`commit-save --turn 0`。
初期配分が完了する前に冒険ターンを1へ進めない。既存の冒険を再開する時は、
完了済みの導入をやり直さず、現在の確定turnを保持する。

| 意味 | 正しいJSON pointer |
|---|---|
| 日付 | `/world_state/day` |
| 時間帯 | `/world_state/time_of_day` |
| 借金元本 | `/debt_state/principal` |
| 借金の表示互換値 | `/player/debt`。元本と同時更新 |
| 借金台帳 | `/debt_state/collection_ledger` |
| クエスト進捗 | `/world_state/quest_card/progress`全体をreplace |
| クエスト終了 | `/world_state/quest_card`をnullへreplace |
| 報酬台帳 | `/world_state/reward_ledger` |

例えば進捗にまだ存在しない中間項目へaddするのではなく、現在のprogress全体を
読み、必要な既存項目を保った完全な辞書へ更新する。

```json
{"op":"replace","path":"/world_state/quest_card/progress","value":{"stage":"settle","completed_objectives":["実際に完了した目的"]}}
```

これは形の例。物語上まだ達成していない目的を、例の文で完了扱いにしない。

## 2. 現金報酬1成分の精算例

前提：依頼は完了・受取合意済みで、現在のカードにoffered=trueの報酬契約がある。
この例は現金1成分だけ。品物・権利・保留等がある契約を、この形へ削らない。
最初に次の値を今回の実パス・一意IDへ置く。作業ファイルはstate/runtime内。

```bash
export MACHADAN_TOOL="$HOME/workspace/machadan_spade/muse版/tools/machadan_runtime.py"
export TASK_SAVE=/absolute/path/to/committed.yaml
export TASK_PREPARED=/absolute/path/to/tx.prepared.yaml
export TASK_DRAFT=/absolute/path/to/tx.reward.draft.yaml
export TASK_FINAL=/absolute/path/to/tx.reward.final.yaml
export TASK_EFFECT=/absolute/path/to/tx.reward.effect.json
export TASK_TX=reward-settle-unique-id
```

以下で完全な下書きを作る。元の契約のID・payer・kind・detailをそのまま使う。

```python
import copy, os, sys
from pathlib import Path
sys.path.insert(0, str(Path(os.environ['MACHADAN_TOOL']).parent))
import machadan_runtime as rt
current = rt.load_yaml(Path(os.environ['TASK_SAVE']))
candidate = rt.load_yaml(Path(os.environ['TASK_PREPARED']))
card = current['world_state']['quest_card']
contract = card['reward_contract']
assert contract['offered'] is True
assert len(contract['components']) == 1
component = copy.deepcopy(contract['components'][0])
assert component['kind'] == 'gold'
amount = component['detail']['amount']
assert isinstance(amount, int) and amount > 0
assert candidate['player']['gold'] == current['player']['gold']
assert not any(row['settlement_id'] == contract['settlement_id']
               for row in current['world_state']['reward_ledger'])
candidate['player']['gold'] += amount
component.update(state='delivered', transaction_id=os.environ['TASK_TX'],
                 effect={'target':'player.gold', 'amount':amount,
                         'before_sha256':'PENDING', 'after_sha256':'PENDING'})
candidate['world_state']['reward_ledger'].append({
    'settlement_id':contract['settlement_id'], 'payer':contract['payer'],
    'status':'settled', 'components':[component]})
candidate['world_state']['quest_card'] = None
# この例は現金の受取と台帳の正形。依頼の達成処理は別途、今回の事実どおりに反映する。
rt.atomic_write(Path(os.environ['TASK_DRAFT']), rt.dump_yaml(candidate))
```

上のPythonを作業用スクリプト等として実行後、現金の実差分からeffectを取得する。
reward-effect自体にファイル出力引数はない。下の`>`はシェルによるstdoutの保存。

```bash
python3 -B "$MACHADAN_TOOL" reward-effect \
  --current "$TASK_SAVE" --candidate "$TASK_DRAFT" --target player.gold > "$TASK_EFFECT"
```

返るJSONのtarget・before_sha256・after_sha256・amountを同じ成分へ入れる。

```python
import json, os, sys
from pathlib import Path
sys.path.insert(0, str(Path(os.environ['MACHADAN_TOOL']).parent))
import machadan_runtime as rt
candidate = rt.load_yaml(Path(os.environ['TASK_DRAFT']))
effect = json.loads(Path(os.environ['TASK_EFFECT']).read_text())
assert effect['ok'] and effect['changed'] and effect['amount'] > 0
row = candidate['world_state']['reward_ledger'][-1]
component = row['components'][0]
assert component['transaction_id'] == os.environ['TASK_TX']
assert effect['amount'] == component['detail']['amount']
component['effect'] = {key:effect[key] for key in
                     ('target','before_sha256','after_sha256','amount')}
rt.atomic_write(Path(os.environ['TASK_FINAL']), rt.dump_yaml(candidate))
```

```bash
python3 -B "$MACHADAN_TOOL" validate-save "$TASK_FINAL"
python3 -B "$MACHADAN_TOOL" commit-save --current "$TASK_SAVE" \
  --candidate "$TASK_FINAL" --transaction-id "$TASK_TX" --turn <次の冒険turn>
```

status・components・effect・payerが揃い、終端精算とカードnullが同じ候補にあることを確認する。
失敗した場合は同じ候補とtx IDを保って修正する。成功した報酬を別IDで作り直さない。

### 依頼の終了差分

現金の例は依頼名・級・達成件数を自動更新しない。依頼そのものが終了した時は、同じ完全候補でworld_state.quest_activeとquest_rankを空にし、実際に達成した級のquests_completedだけ1増やす。既に達成件数を記録済みなら重ねない。報酬辞退・不達成を自動で達成へ数えない。受注可能級の更新は既定の実績条件を使う。

### アイテム・権利・辞退がある場合

元の契約成分を全部維持し、それぞれの受取・辞退・保留を記録する。
品物は`reward-effect --target inventory_bundle`のadded_itemsにある品名・数量と照合する。
契約外の拾得品、購入、薬の使用を同じ精算候補へ混ぜない。
権利はworld_state.entitlementsのeffectと権利IDを結ぶ。辞退・失効はeffect=null。
一括受取の例を使って、未選択の成分を勝手に受取済みにしない。

## 3. 宿代200Gの借金加算例

プレイヤーが実際に宿泊した夜だけ使う。例は本人の通常部屋分200G。
スイートの追加代と仲間の分担は既存契約から別途算出する。
野宿・日付変更だけではこの処理を実行しない。

元本10,000G、夜のDay4、契約IDがlilith-debt-cycle-0なら、候補は次の形。

```yaml
player:
  debt: 10200
# playerの他項目は元の値を全て保持。goldは変更しない。
debt_state:
  principal: 10200
  collection_pending: true  # 翌朝Day5まで進める同じ候補で設定
  collection_ledger:
    # 過去行は全て保持して、次の1行を末尾に追記
    - collection_id: inn-night4-player
      transaction_id: inn-night4-player
      event_kind: charge
      collection_day: 4
      contract_id_before: lilith-debt-cycle-0
      contract_id_after: lilith-debt-cycle-0
      principal_before_payment: 10000
      principal_after_resolution: 10200
      charge_amount: 200
      reason: inn
      source_id: inn-Day4-player
world_state:
  day: 5
  time_of_day: 朝
```

上は差分の説明であり、他項目を捨てたセーブとして保存しない。
実際は完全なprepared候補を複写して元本・表示互換値・台帳・翌朝の日付を同時更新する。
台帳collection_dayは費用を処理する前の夜のDay、日付は翌朝へ進める。
取立日でない夜は、翌朝が次回取立日へ達する場合だけpending=trueへする。
chargeではcollection_serialや請求額を増やさず、宿代を支払い済み請求へ算入しない。

仲間の自己負担が不足した分はreason=member_shortage。その額だけを記録する。
複数のchargeが必要なら、現在の検証器が受け付ける1台帳行ずつ別候補・別tx IDで順に確定する。同じ夜の内部分割は全て同じ対象turnを明示し、最初の候補だけ日付を進める。翌朝の追加charge.collection_dayはその時点の確定Dayを使い、source_idにどの夜の誰の不足かを残す。
本人が明示的に宿代を現金払いした場合は、その金の差分を別に扱い、借金加算を重ねない。
プレイヤーへの宿泊結果は内部commitごとに分断せず、一連の就寝として返す。

## 4. 取立日への到達から解決まで

1. 時間を進める前にnext_collection_dayを読む。その日を越える長い作業は、まず取立日で区切る。
2. 日付をその日にした同じ候補でcollection_pending=trueとする。宿泊なら§3の費用記録も揃える。
3. validate-save→commit-saveで取立て待ちを確定する。日付を先に確定して後からpendingを立てない。
4. 直前の原子的な場面を終え、全額・一部・今回は払わない、を提示して入力を待つ。
5. 選ばれた金額で次を実行する。0Gの不払いも正規の入力。任意の部分払いは100G単位、元本の完済額だけ端数可。

```bash
python3 -B "$MACHADAN_TOOL" resolve-debt-collection --save <取立て待ちの完全候補または確定セーブ> \
  --payment <本人が選んだ額> --output <別の精算候補.yaml> --transaction-id <一意ID>
python3 -B "$MACHADAN_TOOL" validate-save <別の精算候補.yaml>
python3 -B "$MACHADAN_TOOL" commit-save --current <確定済み取立て待ちセーブ> \
  --candidate <別の精算候補.yaml> --transaction-id <同じ一意ID> --turn <現在の確定turn+1>
```

宿泊後にプレイヤーの返済入力を受けた取立て処理は新しい冒険turn（確定turn+1）にする。同じ選択を内部で分割して記録するだけなら同じ対象turnを保つ。導入のturn0とは区別する。

例：残元本10,200Gを全部返す入力なら--payment 10200。単に今回請求500Gを払う入力なら--payment 500。
前者では元本全額の完済台帳と解禁、次契約50,000Gへの更新まで同じ候補で確定する。
後者では今回の支払い・残元本・次回請求だけを更新する。どちらも次回取立日+5日、pending=false。
全額を払えなくても、一部・不払いの既定加算以外の罰を作らない。

pendingが真の間は、次の日付や次の通り抜けへ進めない。同じ取立てを別tx IDで再処理しない。
取立てのために戦闘の途中を中断したり、同じ報酬をもう一度受け取ったりしない。

## 5. 納品時の確認と既存セーブ

`tools/check_release_v413.py`は精算・宿代・取立て・表示の正形と、凍結した逐語文を検証する納品用検査。
毎ターンや語彙の機械検査へ接続しない。q節の本文は変更しない。
セーブv3と既存の必須項目を維持し、passage_ticksは通過を初めて使った時だけ0から補う。
既存の人物・配分・所持品・日次資源・進行中の戦闘の確定数値は更新で再作成しない。

旧v3の保存構造の変換は不要だが、設置時は既存migrate-saveでgame_versionとcontent_manifest_hashを現行へ更新し、再検証する。これを人物・配分・進行の再生成へ読み替えない。
