# 職業・店舗・商品開発システム (M92)

この文書は、プレイヤーが「○○屋」を営む、職業知識で街の事件を解く、
未知素材を調べて新商品を作る時の正本である。通常クエストの物語カードは
`イベントクエスト設計書.md`、既存品と性能上限は
`世界/Item_Database.md`、判定式は `判定基準シート.md` を併用する。

## [ENTERPRISE_PRINCIPLES] 1. 基本原則

1. **冒険職と商売は別軸**: `player.job` を変えても、確立済みの店・工房、
   レシピ、顧客、専門実績は消えない。逆に「鍛冶師」と名乗るだけで設備や
   商業レシピを自動取得しない。
2. **物語が主、経営表が従**: 店は毎日の自動収入装置ではなく、人と問題に
   出会う拠点である。受けた依頼は相談、調査、選択、実使用、余韻を持つ。
3. **奇妙さと危険度を分離**: 変わった依頼が必ず高難度とは限らず、重大な
   依頼が必ず奇抜とも限らない。
4. **専門性は数値ボーナスだけにしない**: 専門家だけが扱える工程、気付ける
   意味、使える設備、正式に保証できる成果で差を出す。
5. **一話は完結**: その依頼の困り事、真相、契約はその回で閉じる。完成品、
   評判、顧客関係、街の変化から後日の独立依頼が生まれることは許す。
6. **利益は実体を伴う**: 材料、時間、設備、需要、報酬契約なしに金や商品を
   増やさない。安全な街で同じ行動を連打する無限金策を禁止する。

## [PROFESSION_PROFILE] 2. 職業プロフィール

職業名とは別に、主人公と仲間は次を持つ。自由入力の職業名から毎回推測せず、
登録・転職・習得時に固定し、明示的な変更だけを記録する。

```yaml
job_profile:
  combat_role: frontline | hybrid | backline | noncombat
  magic_role: noncaster | hybrid | caster | specialist
  expertise_tags: []
  solo_suitability: good | difficult | unsuitable
  party_needs: []
```

`expertise_tags` の標準例は、鍛冶、調合、医療、料理、服飾、木工、建築、
魔道具、鑑定、商売、運送、採集、農業、宿屋、芸能、法務、帳簿、交渉である。
自由タグも許すが、既存タグの言い換えだけで別の効果を重ねない。

- **一致分野**: 専門設備・完成工程を扱える。基本観察から専門的意味を自動で
  1つ得るか、該当判定の難易度を1段階下げる。両方は同時に得ない。
- **隣接分野**: 通常難易度で扱う。保証・量産には一致分野の協力が要る場合がある。
- **未訓練**: 観察・運搬・補助はできる。危険な完成工程は1段階難しくするか、
  専門家との共同作業を必要とする。重要手掛かり自体は消さない。

専門補正も通常の補正上限に含める。職業名だけを根拠に恒久的な+3以上を作らない。
同じ専門性による難度低下と同分野の技能加算は、判定基準M100に従い有利な一方だけ。
別根拠の関係・道具等は既定上限内で併用でき、装備や火による能力値増加は別枠とする。

## [ENTERPRISE_STATE] 3. 永続状態

店舗・発見・研究・レシピはセーブの次の領域へ保存する。表示用の名前ではなく、
安定IDで相互参照する。

```yaml
enterprise_state:
  version: 1
  businesses:
    - business_id: "BUS-..."
      name: ""
      profession_label: ""
      profession_tags: []
      location_id: ""
      status: proposed | open | suspended | closed
      established_day: 1
      facilities: []
      reputation:
        local: 0
        guild: 0
        specialties: []
      last_customer_roll_day: null
      active_order_id: null
      catalog_recipe_ids: []
      warehouse_ref: "inventory.warehouse"
  discoveries: []
  research_projects: []
  recipes: []
  order_book: []
  commerce_ledger: []
  reputation_ledger: []
  lilith_investments: []
  community_threads: []
  aftermath_seeds: []
```

店舗成立は、プレイヤーが名称、業種、場所を明示的に決め、必要な権利・設備・
費用を満たした時だけ記録する。`proposed` は構想中で客を取れない。転職だけでは
店舗状態や専門タグを変更しない。

### 3.1 倉庫と冒険バッグ

- 店舗・宿の倉庫は冒険用の共有バッグと別領域で、潜行中には使えない。
- 倉庫の実体は `inventory.warehouse` だけに置き、各店の独自在庫一覧へ複写しない。
  `warehouse_ref` はその参照先であり、所持数の正本ではない。
- バッグから倉庫、倉庫からバッグへの移動は街での明示操作として記録する。
- 注文へ予約した素材は、バッグまたは倉庫の元の場所に残り、枠を使うが、
  使用・売却・別注文への予約はできない。
- 未知素材を持ち帰れず現場へ置く場合は、その場で保管先を作った事実がない限り
  所持扱いにしない。

### 3.2 借金の段階解禁と事業の分離 (M103/M104)

完済特典は運用詳細シート§8に従う。第一段階はリリスとの関係解禁だけ、
第二段階はリリスとネームドの外見・体型変更。完済更新時に店舗設備、調達網、
緊急回収、現金、追加能力を自動付与せず、3択や暫定特典の選択待ちも発生しない。
`enterprise_state.lilith_investments`の存在を段階解禁の根拠にしない。

通常の施設購入・研究・商談・仕事の報酬は、この完済特典とは別に既存ルールで行う。
正規の代金、材料、時間、報酬契約を必要とし、恋愛や借金更新を理由に無料扱いにしない。

### 3.3 街の問題と変化

職業事件や商品使用が街へ残した結果は、自由文の記憶だけでなく次へ保存する。

```yaml
community_threads:
  - thread_id: "COM-..."
    location_id: ""
    status: latent | active | resolved | changed
    problem: ""
    affected_npc_ids: []
    fixed_facts: []
    profession_hooks: []
    consequence_flags: []
    source_case_id: null
```

`resolved` は元の問題が解決済み、`changed` は解決の結果として場所・住民・需要が
変わった状態である。`changed` を同じ未解決事件の継続に使わず、後日の別依頼へ
採用する時は `aftermath_seeds[]` から新しいカードを作る。

## [SHOP_OPENING] 4. 店を開ける

1店舗につき、新規客の生成はゲーム内1日1回までである。
`last_customer_roll_day == world_state.day` なら、同じ日に再び「店を開ける」と
言っても新しい有償依頼・日常売上を生成しない。会話、製作、既存客への対応、
店内描写は行える。

未処理の `active_order_id` がある店では新しい有償注文を受けない。店を開けた時は、
先に進行中注文を続けるか、休業・破棄・再交渉するかを提示する。

新規客を探せる日は、カードを3枚完成させる前に次の3つの短い候補を提示する。

1. **小さな依頼**: 日常規模。E〜D級、1〜3ターン、原則戦闘なし。
2. **実力相応の専門依頼**: 現在の専門実績・受注可能級・店舗評判に合う。
3. **変わった依頼**: 奇妙な用途、依頼人、制約のいずれかを持つ。危険度は別に表示。

受けるのは原則1件だけ。選んだ候補だけ完全な `quest_card` を生成し、他の2件は
未受注の短い相談として閉じる。断ることに機械的ペナルティはない。

### 4.1 規模と奇妙さ

```yaml
work_classification:
  scope: routine | specialist | major | civic
  risk_rank: E | D | C | B | A
  weirdness: ordinary | unusual | bizarre
```

| scope | 目安 | 内容 |
|---|---|---|
| routine | E〜D | 個人や一店舗、1〜3ターン、軽い損失まで |
| specialist | C | 3〜6ターン、調査・試作・現地確認 |
| major | B | 5〜8ターン、複数人・地区・危険現場へ影響 |
| civic | A | 5〜8ターン、都市規模。原則パーティ・組織協力が必要 |

`weirdness` は報酬倍率ではない。奇妙だから高額、高難度だから奇抜、という自動変換を
しない。C級以上は受注可能級に加え、必要な専門タグ・設備・実績を満たすか、
不足分を補う協力者を契約する。

### 4.2 収入

- 日常営業を宣言するだけの自動収入は当面実装しない。
- 金銭・品物・権利は、受注時に固定した `reward_contract` と材料契約で清算する。
- 商業レシピは将来の依頼・量産注文を解禁するが、所持しているだけで金を生まない。
- 同一商品を売る場合も、需要数、在庫、材料、買い手、価格をその営業単位で固定する。

## [PRODUCTION_COMMISSION] 5. 生産依頼

生産依頼は、指定品製作、新規発明、悩み解決の3型を使う。物語の基本線は
**相談と困り事の実景 → 職業知識による調査 → 街・道中・ダンジョンでの調達 →
設計・試作 → 性能と安全等の選択 → 現場での実使用 → 商品・評判・関係の結果**
である。工程の順序と解決方法は強制しない。

注文には次を追加する。

```yaml
commission:
  order_id: "ORD-..."
  business_id: "BUS-..."          # 店舗外の単発仕事ならnull
  scope: routine | specialist | major | civic
  risk_rank: E | D | C | B | A
  weirdness: ordinary | unusual | bizarre
  required_expertise: []
  required_facilities: []
  checks_max: 2
```

重要判定は合計2回までを標準とする。失敗は同じ判定の振り直しではなく、時間、
材料、性能、安全性、外見、秘密、専門家への依頼のいずれかの妥協へ変える。
プレイヤーが撤退しない限り、「判定失敗なので何も作れず物語終了」だけに固定しない。

`order_book` は依頼の現在状態、取引台帳は確定済みの差分を持つ。受注中の
条件と履歴を同じ自由文で兼用しない。

```yaml
order_book:
  - order_id: "ORD-..."
    business_id: "BUS-..."
    quest_id: "QST-..."
    work_kind: production_commission | professional_case | sale
    status: offered | active | settled | cancelled | failed
    accepted_day: 1
    deadline: null
    contract_hash: ""
    stage: consultation
    reservation_ids: []
    aftermath_seed_ids: []
commerce_ledger:
  - transaction_id: "TX-..."
    order_id: "ORD-..."
    day: 1
    kind: expense | sale | reward | refund
    gold_delta: 0
    item_deltas: []
    note: ""
reputation_ledger:
  - reputation_tx_id: "TX-..."
    business_id: "BUS-..."
    day: 1
    local_delta: 0
    guild_delta: 0
    specialty_changes: []
    reason: ""
```

`commerce_ledger` と `reputation_ledger` は追記専用で、確定後の行を上書き・削除
しない。`businesses[].active_order_id` は、同じ店の `order_book` にある
`status: active` の1件と常に一致させる。
`commerce_ledger` は事業用の監査記録で、その行から所持金・所持品を再適用しない。
クエスト報酬の実体はM83の `reward_ledger` と同じ `transaction_id` で一度だけ
反映する。`businesses[].reputation` は `reputation_ledger` を積み上げた表示値と一致させる。

`order_book` が注文進行と予約IDの永続正本である。`quest_card.commission` は
受注時の不変条件、`quest_card.progress` はプレイ中の表示とし、同じ `order_id`
を参照する。段階、判定回数、予約、完了結果を変えるターンは、
`order_book` と `quest_card.progress` を同一transactionで整合させる。

### 5.1 材料予約と原子的な清算

予約の実体は注文カードへ複写せず、共有インベントリの正規領域へ置く。
注文は `reservation_ids` だけを参照する。

```yaml
inventory:
  reservations:
    - reservation_id: "RSV-..."
      source_id: "ORD-..."       # 注文IDまたは研究ID
      stack_id: "STK-..."       # stack_id / instance_id のどちらか一方
      instance_id: null
      quantity: 1
      status: reserved | consumed | returned | lost
```

受注時に期限、予算、材料費負担、支給品、完成品の所有、予約対象を一括で固定する。
予約後の品は元のバッグまたは倉庫に残し、売却・使用・移動・別注文へ流用
できない。バッグ内の固有品も予約中は元の枚数だけ所持枠を使う。試作・完成・破損の
処理では、材料の
消費または返却、注文進捗、成果物、報酬、評判、ログを同じtransactionで確定する。
失敗したtransactionではどれも変えない。再交渉は依頼人との合意と履歴を記録し、
元の契約を無言で上書きしない。

## [PROFESSIONAL_CASE] 6. 職業事件

製作物を必要としない鑑定、診断、毒物分析、建築事故、帳簿不正、偽造判定、
故障原因、衛生問題、危険物封じ等は `professional_case` とする。

```yaml
work_kind: professional_case
case:
  case_id: "CASE-..."
  business_id: null
  profession_basis: []
  case_type: diagnosis | forensics | repair | safety | mediation | containment
  scope: routine | specialist | major | civic
  risk_rank: E | D | C | B | A
  weirdness: ordinary | unusual | bizarre
  presenting_problem: ""
  client_belief: ""
  fixed_facts: []
  hidden_cause: ""
  evidence: []
  false_assumption: ""
  expertise_hooks: []
  deadline: ""
  stakes: ""
  completion_criteria: []
  consequence_rules: []
  town_effect_rules: []
  open_solution: true
```

### 6.1 手掛かりの契約

- 固定事実を最低3つ、真相へ届く証拠経路を最低2つ用意する。
- 基本観察で得る情報を判定失敗で消さない。
- 一致する専門性は、その情報の意味、原因候補の除外、危険な次工程の予告の
  いずれかを自動で1つ与える。真相そのものを無条件で全部開示する必要はない。
- 重要な一回の失敗で進行不能にしない。失敗は時間経過、証拠の不完全、危険増大、
  費用、関係悪化へ変換する。
- `client_belief` や `false_assumption` を誤りと決めた場合、その根拠となる証拠を
  カード生成時に固定する。プレイヤーの正しい指摘を潰す後付け真相を禁止する。
- 専門家でない解決も許す。別証拠、協力者、隔離、応急策などを同じ達成条件で裁定する。

## [DISCOVERY_RESEARCH] 7. 未知素材と研究

未知素材は通常の名前付きスタックへ混ぜず、取得時点で正体・性質・危険性を固定する。

```yaml
discoveries:
  - discovery_id: "DISC-..."
    provisional_name: ""
    source: {kind: dungeon | quest | event, source_id: "", location: "", day: 1}
    tier: 1
    status: unknown | identified | validated | depleted
    item_instance_ids: []
    observed_traits: []
    confirmed_traits: []
    sealed_truth: {}
    hazards: []
    possible_uses: []
```

未知素材の実物と所在は `item_instances` と `inventory` が正本で、
`discoveries` へ数量やバッグ位置を複写しない。`item_instance_ids` は同じ発見から得た
固有素材だけを参照する。該当個体の `item_def_id` が指す
`item_definitions[].provenance.discovery_id` も同じIDを持つ。
研究・試作で消費する時も、先にその個体を `inventory.reservations` へ予約する。

| 入手帯 | discovery tier | 製品上限の目安 |
|---|---:|---|
| 1〜2F／E〜D級 | 1 | Item Tier 1 |
| 3〜4F／C級 | 2 | Item Tier 2 |
| 5〜6F／B級 | 3 | Item Tier 3 |
| 7〜9F／A級 | 4 | Item Tier 4 |

未知だから既存の装備、魔法、消耗品上限を超えてよい、とはしない。高Tier素材を
低い設備で扱う場合は、研究の中断、専門家協力、設備取得等を選べるようにする。

研究は次を保存する。

```yaml
research_projects:
  - project_id: "RSH-..."
    discovery_ids: []
    design_goal: ""
    phase: analysis | prototype | field_test | complete
    checks_used: 0
    checks_max: 2
    reservation_ids: []
    constraints: []
    tradeoff_rules: []
    prototype_item_id: null
    recipe_candidate: {}
```

研究失敗も生産依頼と同じく、時間、追加材料、性能、安全性、外観、専門家の協力の
選択へ変える。成功するまで同じ判定を繰り返さない。

## [RECIPE_COMMERCIALIZATION] 8. レシピと商品化

試作品ができただけでは商用品にならない。現場試験または依頼人の使用結果を経て、
プレイヤーが商品化を明示した時だけ `validated` または `commercial` にする。

```yaml
recipes:
  - recipe_id: "RCP-..."
    name: ""
    product_kind: ""
    status: prototype | validated | commercial
    source_discovery_ids: []
    inputs: []
    facilities_required: []
    expertise_required: []
    time_cost: ""
    output_spec: {}
    balance_anchor: "既存品名またはItem Tier"
    unit_cost_g: 0
    owner_business_id: null
```

`output_spec` は効果、補正、重量、使用回数、デメリット、対象、品質を完全に保存する。
装備・商品は名前でなく安定IDを持つ `item_instance` として生成する。同名の商品でも
性能が違えば別定義にする。

商品化の効果は、カタログ登録、同種依頼の候補化、事件の解決手段、量産注文の解禁で
ある。自動収入や無料複製ではない。販売のたびに在庫・材料・需要と契約を処理する。

## [PLAYER_CRAFTING_VS_TETRA] 9. プレイヤー製作とテトラ発注

- **テトラ発注**: `Item_Database` のNPCサービス。テトラへ素材と工賃を払い、
  テトラの設備・技術で完成させる。プレイヤーの生産判定を使わない。
- **プレイヤー製作**: 自身または店舗の専門タグ、設備、レシピ、時間、直接経費を
  使う。テトラへの工賃は払わない。ただし燃料、借用設備、外注工程等の実費は払う。
- **共同製作**: 誰が担当する工程、費用、成果物の所有、レシピ共有の有無を受注時に
  固定する。

どの経路でも `Item_Database` のTier上限を超えない。プレイヤー製作だから無料、
テトラと親しいから原価ゼロ、とはしない。

## [AFTERMATH_SEED] 10. 完結と後日依頼

各依頼・事件はその回で完結させる。未回収の黒幕、正体未定の品、意味深な台詞を
将来用に残してはならない。ただし、完結済みの結果から生じる次の事実は保存できる。

```yaml
aftermath_seeds:
  - seed_id: "AF-..."
    source_quest_id: ""
    completed_fact: ""          # 完成品、評判、紹介、街の変化等
    eligible_after_day: 1       # 完了日より後のworld_state.day
    possible_hook: ""
    forbidden_unresolved_mystery: true
    status: dormant | used | retired
```

例は「以前作った義手を見た別の客から相談が来る」「救ったパン屋が患者を紹介する」
「浄水剤の普及で別地区から量産注文が来る」である。採用時は新しい独立クエストカードを
作り、元の依頼を再開しない。採用しなくても罰や未解決扱いは生じない。

## [ENTERPRISE_TRANSACTIONS] 11. 更新契約

次の変更は、関連する実体差分と同一transactionで確定する。

- 店舗成立・休業・閉店
- 注文受注と材料予約
- 予約材料の消費・返却・喪失
- 発見登録、研究段階、試作品生成
- レシピ検証・商品登録
- 報酬、在庫、評判、街の状態、`aftermath_seeds`

片方だけ更新された候補は拒否する。`last_customer_roll_day` は候補提示を実際に行った
時点で更新し、断ったからといって同日の再抽選を許さない。表示上の所持枠・在庫数・
予約数は保存済み一覧から毎回再計算し、要約値だけを信頼しない。
