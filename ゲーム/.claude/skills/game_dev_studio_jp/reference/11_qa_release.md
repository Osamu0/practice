# 11 品質保証・最終審査

完成と言ってよいかを決める部門。テスト、技術要件と素材の確認、リリース判定をする。

## 仕事人と呼ぶ順

1. `game-qa-tester`（テスト計画 → 実行 → バグ報告）と `game-qa-compliance`（技術要件と素材の確認）を**同時に**
2. 見つかったバグは 10 の `game-beta-bugfix` に戻して直し、`game-qa-tester` が回帰テストで閉じる
3. 確認の「否」は、持ち主の部門に戻して直す（素材の差し替え、クレジットの追加、文言の直し）
4. 全部そろったら `game-qa-release-judge`
5. 判定をオーナーに渡して **ゲートD**

## テストの範囲（既定）

- 機能：すべての受け入れ条件
- 境界：0、最大、同時、連打
- 中断：ポーズ、タブの切り替え、画面の大きさを変える、途中で閉じる
- 保存：保存と読み込み、古い版のセーブ（アップデート時）
- 長時間：30分以上の連続プレイで重くならないか
- 性能：目標のフレームレート
- 表示：画面の大きさ、文字の切れ、ローカライズ
- アクセシビリティの設定が効くか

## 確認の項目（既定）

- 対象プラットフォームの技術要件（画面、入力、中断、保存。その時点の公式の資料で確かめる）
- 素材、フォント、ライブラリの使い方とクレジット
- 既存の作品に似すぎていないか
- 仮の資産が残っていないか（残すなら理由）

## リリースの条件

- きれいな状態から同じビルドが作れる
- 自動テストが全部通る。テスト計画の項目が全部合格か、残す理由がある
- 致命・重大のバグが0
- 確認の「否」と「わからない」が0（「わからない」が残るなら、オーナーに伝えて決めてもらう）
- 版番号、変更履歴、クレジットがそろっている

（「マスターアップ／ゴールド」は、出すと決めた最終のビルド。このスキルでは、ゲートDを通ったビルドをそう呼ぶ）

## ゲートD（オーナー）

- リリース判定が「出せる」
- オーナーが「出す」と言った。出したら、版のタグを付けてコミットする

## この部門に加わる仕事人

中心の仕事人（上の「呼ぶ順」）に加えて、プロジェクトに要るときに呼ぶ。`開発チーム.md` で使わないと決めた仕事人は呼ばない。

| 仕事人 | 職種 | この部門でやること |
|---|---|---|
| `game-tech-director` | テクニカルディレクター | リリース前に、技術面で出せるかを判定する |
| `game-tech-security` | セキュリティエンジニア、セキュリティテスター、不正対策担当 | セキュリティのテスト（自分たちのビルドに対してだけ） |
| `game-tech-performance` | パフォーマンスエンジニア、パフォーマンステスト担当 | 性能のテスト（目標の端末・画面の大きさで） |
| `game-tech-platform` | プラットフォームエンジニア | 端末ごとの技術要件を満たしているか確かめる |
| `game-pm-manager` | プロジェクトマネージャー、プロダクションマネージャー、制作進行担当、リソースマネージャー、アシスタントディレクター | リリースまでの残りの段取り |
| `game-qa-lead` | QAディレクター、QAマネージャー、QAリード、リードQA | テストの範囲の最終の決めと、品質の報告 |
| `game-qa-automation` | 自動テストエンジニア | リリース前に全部のテストを流す |
| `game-qa-load-compat` | 負荷テスト担当、互換性テスト担当 | 負荷のテスト（自分たちのサーバーに対してだけ）と、互換性の最終の確かめ |
| `game-loc-director` | ローカライズディレクター、翻訳コーディネーター | 言語ごとの最終の確かめの段取り |
| `game-loc-lqa` | LQAテスター、言語監修者 | 直したあとの最終のLQA |
| `game-ops-infra` | サーバー運用担当、インフラエンジニア、SREエンジニア、データベース管理者、サーバー事業者スタッフ | 本番の構成、出し方、見張り、バックアップの手順書 |
